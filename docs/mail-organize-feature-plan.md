# Xi-Mail 邮箱收纳功能整体开发文档

## 1. 文档目的

本文档用于指导 Xi-Mail 新增“邮箱收纳”能力的完整开发、联调、验收与上线。目标是把收件箱、已发送、草稿箱中的邮箱管理方式统一起来，让页面保持简洁，同时保留“按需解放”和“再次收纳”的灵活操作能力。

本方案特别满足以下诉求：

- 收件箱、已发送、草稿箱都支持“收纳”。
- 支持按域名收纳。
- 支持多选邮箱后批量收纳。
- 在收纳区内可将单个邮箱“解放”出来。
- 已解放的邮箱支持再次收纳。
- 原收件箱中的“邮箱分类”能力整体并入“收纳”，不再保留独立分类入口。
- 每完成一个阶段功能，必须先验收；验收通过后，才能进入下一阶段开发。

## 2. 当前系统基线

结合当前代码仓库，现状如下：

- 收件箱已存在“按域名分组/筛选”的前端逻辑，主要位于 `mail-view/src/views/email/index.vue` 与 `mail-view/src/layout/account/index.vue`。
- 已发送页 `mail-view/src/views/send/index.vue` 复用了邮件列表组件，但没有独立的邮箱收纳能力。
- 草稿页 `mail-view/src/views/draft/index.vue` 当前基于浏览器 IndexedDB（`mail-view/src/db/db.js`）保存草稿，尚未提供按邮箱维度的统一管理与收纳入口。
- 后端 `mail-worker/src/service/account-service.js` 与 `mail-worker/src/service/email-service.js` 目前没有“收纳规则 / 解放规则 / 收纳日志”数据结构。
- 收件箱的“域名分类”是前端筛选态，不是持久化业务规则；这意味着本次改造可以直接迁移为“收纳规则”，无需历史数据搬迁。

## 3. 产品目标

### 3.1 用户目标

- 让用户在邮箱数量较多时，首页仍然保持干净、好找、好用。
- 让用户可以按域名快速折叠同类邮箱。
- 让用户可以把少量常用邮箱从收纳中释放出来，作为常驻可见邮箱。
- 让用户在不同页面中拥有一致的管理方式，不用重复学习。

### 3.2 管理员目标

- 能查看用户邮箱收纳状态。
- 能帮助用户批量收纳、批量解放、恢复默认规则。
- 能快速判断“某个邮箱为什么被收纳 / 为什么处于解放状态”。
- 能在上线与回滚阶段快速排障。

## 4. 功能范围

### 4.1 本次范围内

- 收件箱收纳
- 已发送收纳
- 草稿箱收纳
- 域名收纳
- 多选邮箱收纳
- 单个邮箱解放
- 再次收纳
- 收纳规则持久化
- 管理员查看与操作入口
- 验收门禁流程

### 4.2 本次范围外

- 自定义命名收纳分组
- 自动化时间规则（例如 7 天未使用自动收纳）
- AI 自动推荐收纳
- 跨用户共享收纳模板
- 邮件内容级别的自动归类

## 5. 术语定义

- 可见区：当前页面直接展示的邮箱列表。
- 收纳区：已被折叠隐藏、但仍可继续管理的邮箱集合。
- 解放：把某个邮箱从收纳区恢复到可见区。
- 再收纳：把已解放的邮箱重新放回收纳区。
- 作用域（scope）：收件箱 `inbox`、已发送 `sent`、草稿箱 `draft`。
- 域名收纳规则：对某个域名在某个作用域下的默认收纳策略。
- 单邮箱覆盖规则：对单个邮箱在某个作用域下的例外处理，用来支持“从域名收纳中单独解放”。

## 6. 核心业务规则

### 6.1 作用域独立

同一个邮箱在不同页面的状态相互独立：

- 某邮箱可以在收件箱中被收纳；
- 同时在已发送中保持可见；
- 也可以在草稿箱中再次被收纳。

### 6.2 收纳方式

支持两种主方式：

- 域名收纳：例如将 `@demo.com` 在收件箱作用域下整体收纳。
- 多选收纳：在当前作用域下勾选多个邮箱后直接收纳。

### 6.3 域名收纳优先采用“规则 + 例外”模型

为了满足“按域名收纳后，还能在收纳中单独解放某些邮箱”，推荐采用下面的判定模型：

1. 先看当前作用域是否命中了域名收纳规则。
2. 再看该邮箱是否存在单邮箱覆盖规则。
3. 若存在“解放覆盖”，则该邮箱保持可见。
4. 若存在“再次收纳覆盖”，则该邮箱保持收纳。
5. 若无覆盖，则继承域名规则。

该模型的好处：

- 支持“整域名收纳”。
- 支持“单独解放某个邮箱”。
- 支持将已解放邮箱再次收纳。
- 支持未来同域新邮箱自动继承收纳规则，避免页面再次变乱。

### 6.4 新增邮箱继承规则

推荐规则如下：

- 若某域名在某作用域下已被收纳，则该域名下新创建邮箱默认进入收纳区。
- 若管理员或用户后续将某个新邮箱单独解放，则写入单邮箱覆盖规则。

该行为建议在第一阶段验收时确认，不通过则退回为“仅对已存在邮箱生效”的简化策略。

### 6.5 删除、转移、禁用时的联动

- 邮箱被删除后，其收纳规则覆盖项同步失效。
- 邮箱转移到新用户后，不继承原用户的个人收纳覆盖项。
- 域名规则属于用户维度，不跟随邮箱转移。
- 管理员禁用用户时，不删除其收纳数据，只冻结展示与操作。

## 7. 交互方案

## 7.1 总体交互结构

每个作用域都统一为两层管理：

- 第一层：可见区，只展示当前需要直接操作的邮箱。
- 第二层：收纳区，展示已收纳邮箱及域名分组，并提供解放/再次收纳入口。

建议 UI 入口：

- 在邮箱侧栏顶部增加“收纳”入口按钮。
- 在右上角增加“批量收纳”操作按钮。
- 收纳区内默认按“域名分组 + 单邮箱列表”展示。

### 7.1.1 统一收纳弹框规范

收件箱、已发送、草稿箱统一使用同一套“收纳弹框”规范，避免用户在不同页面反复学习。

弹框规范如下：

- 弹框头部展示当前作用域，例如“收件箱 / 已发送 / 草稿箱”。
- 弹框正文必须支持纵向滚动，邮箱数量较多时不能把弹框撑出屏幕。
- 桌面端优先使用双区布局：
  - 左侧为“当前可见邮箱”
  - 右侧为“已收纳邮箱”
- 桌面端弹框需要定位在左侧导航与邮箱菜单右侧的可用内容区中心，避免压住菜单主体。
- 移动端自动退化为纵向堆叠布局。
- 顶部展示摘要统计，至少包含：
  - 当前可见邮箱数
  - 已收纳邮箱数
- 可见区保留多选收纳、单邮箱收纳、按域名收纳。
- 收纳区保留域名折叠展开与单邮箱解放。
- 弹框内文案、样式、按钮位置在三个作用域中保持一致，仅作用域标题不同。

## 7.2 收件箱

当前收件箱已有域名分组筛选，本次调整为：

- 移除 `mail-view/src/views/email/index.vue` 中现有的域名下拉筛选入口。
- 把“按域名查看”改为“按域名收纳”。
- 用户在收纳区点击某个域名组后，可展开查看组内邮箱。
- 用户可在组内对单个邮箱执行“解放”。
- 解放后的邮箱立即回到收件箱可见区。
- 用户可对解放出来的邮箱再次执行“收纳”。
- 收件箱收纳弹框遵循“统一收纳弹框规范”。

## 7.3 已发送

已发送页沿用收件箱的交互模型，但不再依赖原收件箱的分类状态：

- 支持批量勾选邮箱后收纳。
- 支持按域名一键收纳。
- 支持在收纳区内按单邮箱解放。
- 支持再次收纳。
- 已发送必须复用同一套收纳弹框组件，仅标题切换为“已发送”。
- 已发送弹框同样要求内容可滚动，不能因历史发件邮箱数量过多造成弹框不可操作。

## 7.4 草稿箱

草稿页当前缺少统一的邮箱侧管理能力，本次需要补齐：

- 草稿页接入邮箱维度过滤能力。
- 草稿记录按 `accountId` 进行可见区 / 收纳区判定。
- 本地草稿库增加 `accountId` 索引，避免后续按邮箱筛选时全表扫描。
- 草稿页建议与收件箱、已发送共用同一套收纳组件和交互文案。
- 草稿箱必须复用同一套收纳弹框组件，仅标题切换为“草稿箱”。
- 草稿箱弹框同样要求内容可滚动，并在无草稿或某邮箱无草稿时给出空态提示。

## 7.5 管理员入口

管理员建议在 `mail-view/src/views/user/index.vue` 的“用户邮箱”弹窗基础上扩展：

- 增加“收纳状态”列。
- 增加当前作用域切换器（收件箱 / 已发送 / 草稿箱）。
- 增加按域名批量收纳、批量解放入口。
- 增加“查看规则来源”入口，区分：
  - 域名规则继承
  - 单邮箱手动收纳
  - 单邮箱手动解放

## 8. 技术方案

## 8.1 前端改造点

建议重点改造以下模块：

  - 移除对 `domainGroup` 的显示依赖。
  - 支持按当前路由作用域切换收纳配置（收件箱 / 已发送 / 草稿箱）。
- `mail-view/src/views/email/index.vue`

  - 接入收纳态后的可见邮箱列表。

  - 复用统一收纳弹框。
- `mail-view/src/views/draft/index.vue`
  - 新增按 `accountId` 的过滤逻辑。

  - 复用统一收纳弹框。

  - 删除或废弃旧的 `domainGroup` 前端筛选态。
  - 新增收纳状态、规则摘要、当前作用域可见邮箱列表等状态。
- 新增建议文件：
  - `mail-view/src/request/account-storage.js`
  - `mail-view/src/components/account-storage-panel/index.vue`
  - `mail-view/src/composables/useAccountStorage.js`

## 8.2 后端数据模型

推荐新增三张表，而不是继续在 `account` 表上硬加多个页面字段。

### A. 域名收纳规则表 `account_collect_rule`

建议字段：

- `rule_id`
- `user_id`
- `scope`：`inbox | sent | draft`
- `rule_type`：固定为 `domain`
- `rule_value`：例如 `@demo.com`
- `status`：启用 / 停用
- `create_time`
- `update_time`
- `updated_by`

作用：

- 保存“某用户在某页面下，对某域名启用了收纳”。

### B. 单邮箱覆盖表 `account_collect_override`

建议字段：

- `override_id`
- `user_id`
- `account_id`
- `scope`
- `display_state`：`visible | collected | inherit`
- `source_type`：`manual_release | manual_collect | admin_release | admin_collect`
- `create_time`
- `update_time`
- `updated_by`

作用：

- 用于支持“域名已收纳，但单独解放某个邮箱”。
- 用于支持“已经解放的邮箱再次收纳”。

### C. 收纳日志表 `account_collect_log`

建议字段：

- `log_id`
- `user_id`
- `account_id`
- `scope`
- `action`：`domain_collect | manual_collect | manual_release | admin_collect | admin_release`
- `operator_user_id`
- `remark`
- `create_time`

作用：

- 给管理员排障与审计使用。
- 用于说明某个邮箱为什么处于当前状态。

## 8.3 后端服务与 API 设计

建议新增独立服务：

- `mail-worker/src/service/account-storage-service.js`
- `mail-worker/src/api/account-storage-api.js`

建议接口如下：

### 用户侧接口

- `GET /account/storage/config?scope=inbox`
  - 返回当前用户在该作用域下的域名规则、单邮箱覆盖、收纳摘要。
- `POST /account/storage/domain-collect`
  - 入参：`scope`, `domain`
  - 行为：为该域名建立或启用收纳规则。
- `POST /account/storage/manual-collect`
  - 入参：`scope`, `accountIds`
  - 行为：对选中的邮箱写入单邮箱收纳覆盖。
- `POST /account/storage/release`
  - 入参：`scope`, `accountIds`
  - 行为：把选中的邮箱写入单邮箱解放覆盖。
- `POST /account/storage/recollect`
  - 入参：`scope`, `accountIds`
  - 行为：将已解放邮箱恢复为收纳态；若命中域名规则则恢复 `inherit`，否则写入 `collected`。
- `GET /account/storage/summary?scope=inbox`
  - 返回收纳区域名统计、邮箱总数、已解放异常项数量。

### 管理员接口

- `GET /admin/account-storage/list?userId=xx&scope=inbox`
- `POST /admin/account-storage/domain-collect`
- `POST /admin/account-storage/release`
- `POST /admin/account-storage/reset`
- `GET /admin/account-storage/log?userId=xx&scope=inbox`

### 与现有接口的关系

- `mail-worker/src/service/account-service.js` 保持账户基础查询职责。
- 收纳逻辑不要直接塞进 `account-service.js`，避免账户基础逻辑继续膨胀。
- `mail-worker/src/service/email-service.js` 仍负责邮件列表；邮箱可见性解析建议在前端统一完成，必要时再扩展服务端过滤。

## 8.4 草稿箱本地数据改造

当前草稿库在 `mail-view/src/db/db.js` 中只有：

- `draft: '++draftId,createTime'`
- `att: 'draftId'`

建议升级为新版本，例如：

- `draft: '++draftId,createTime,accountId'`

原因：

- 草稿收纳需要按邮箱账号筛选。
- 若继续使用当前结构，只能每次全量扫描所有草稿，邮箱数量和草稿数量增多后会变慢。

## 8.5 权限设计

建议新增或细分权限：

- `account:storage:view`
- `account:storage:edit`
- `account:storage:admin`

默认建议：

- 普通用户：拥有自己邮箱的查看与编辑能力。
- 管理员：拥有跨用户查看、编辑、重置、查看日志能力。

## 8.6 迁移策略

本次迁移重点不是“搬历史数据”，而是“替换旧交互”：

- 旧的收件箱域名分类是前端筛选态，不需要写迁移脚本。
- 只需在新版本上线时下线旧的 `domainGroup` UI 与状态逻辑。
- 新规则表上线后，历史用户默认都处于“未收纳”状态。

## 9. 分阶段开发与验收门禁

## 9.1 总原则

每个阶段严格遵循以下流程：

1. 完成功能开发。
2. 开发自测通过。
3. 提交验收清单与演示路径。
4. 业务验收明确通过。
5. 才能进入下一阶段。

若验收不通过：

- 本阶段只允许修复问题，不允许插入下阶段功能。
- 所有后续开发冻结，直到本阶段重新验收通过。

## 阶段一：收件箱收纳基础版

### 开发目标

- 完成收件箱作用域的收纳能力。
- 将原收件箱“邮箱分类/域名筛选”并入收纳。
- 支持按域名收纳、多选收纳、单邮箱解放、再次收纳。

### 代码范围

- `mail-view/src/views/email/index.vue`
- `mail-view/src/layout/account/index.vue`
- `mail-view/src/store/account.js`
- 新增前端收纳请求与收纳面板文件
- `mail-worker/src/init/init.js`
- 新增收纳规则、覆盖、日志表及 API / Service

### 交付结果

- 收件箱页面去掉旧域名分类下拉。
- 收件箱页面增加收纳入口。
- 用户能看到收纳区和可见区。
- 域名收纳与多选收纳可持久化。

### 阶段验收用例

- 用例 1：选择 `@demo.com` 域名执行收纳，收件箱可见区立即隐藏该域名邮箱，收纳区显示该域名组。
- 用例 2：多选 3 个邮箱执行收纳，仅这 3 个邮箱进入收纳区。
- 用例 3：在收纳区中单独解放 1 个邮箱，该邮箱立即回到可见区。
- 用例 4：对已解放邮箱再次收纳，邮箱重新进入收纳区。
- 用例 5：刷新页面、重新登录后，收纳状态仍然正确。
- 用例 6：原“邮箱分类”入口已完全移除，不再出现双入口。

### 通过标准

- 以上 6 个用例全部通过。
- 无明显 UI 阻塞、无数据丢失、无权限越权。

### 未通过时禁止进入

- 已发送收纳
- 草稿箱收纳
- 管理员侧扩展

## 阶段二：已发送收纳

### 开发目标

- 把收纳能力完整复用到已发送作用域。
- 与收件箱共用同一套规则解析与交互框架。
- 与收件箱共用优化后的可滚动收纳弹框。

### 代码范围

- `mail-view/src/views/send/index.vue`
- 通用收纳组件与状态管理
- 后端作用域扩展为 `sent`

### 交付结果

- 已发送页支持按域名收纳。
- 已发送页支持多选收纳。

## 12. 风险与应对

- 风险 1：域名规则与单邮箱覆盖叠加后，状态判断变复杂。
  - 应对：统一封装解析函数，前后端使用同一判定规则。
- 风险 2：草稿仍是本地数据，容易与服务端规则脱节。
  - 应对：草稿页每次进入时重新拉取收纳配置并在本地实时计算。
- 风险 3：管理员批量操作容易误伤。
  - 应对：增加二次确认、操作日志、支持重置。
- 风险 4：旧分类逻辑未彻底清掉，出现双入口。
  - 应对：阶段五专门做死代码清理和回归检查。

## 13. 上线建议

- 先在测试环境按阶段灰度。
- 每阶段验收通过后再合并到主线。
- 最终上线时优先在管理员可控的小范围账号中验证。
- 若出现问题，优先关闭新收纳入口并保留数据，不要立即删规则表。

## 14. 结论

本方案建议把“邮箱分类”升级为“收纳规则系统”，而不是继续停留在前端筛选层。这样才能稳定支持：

- 按域名收纳
- 多选收纳
- 单邮箱解放
- 再次收纳
- 三个作用域独立
- 管理员统一管理

同时，整个开发必须按阶段推进，并严格执行“上一阶段验收通过后，下一阶段才可开始”的门禁机制。
